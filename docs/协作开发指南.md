# 分组、Git 与 AI 交接

A 组双 Codex 的角色绑定、认领、任务队列和交接细则见 [双端协作流程](coordination/README.md)。以下通用规则继续适用。

B 组按 [B1/B2共同任务表](coordination/B.md) 串行工作，共用源码、测试和日志。每次新的开发/调试会话，用户已明确角色就直接记录；没有明确角色必须先询问，不能根据本地 rnc.role、Git账号或上一位使用者推断。同一会话已确认后无需重复问。

## 单仓库分源码

A/B 各自拥有一棵源码目录，纯计算与展示互不依赖；同一个锁文件和契约保证联调可复现。当前四人两周不需要多个仓库增加的版本协调成本。

| 区域 | 负责人 | 约束 |
| --- | --- | --- |
| team-a/app、player、charts | A1 | 通过注入接口消费结果 |
| team-a/viewer | A2 | 不改变声学配置 |
| team-b/** 与B组测试 | B1/B2 串行共用 | 只分任务主责，不按人员限制文件；B1算法/验证，B2数据/分析/导出 |
| shared、integration、配置/CI | A1 + B1 | 记录接口影响，协调合并 |
| fixtures/reference | 基准共管 | 本期只读，不覆盖 |
| 开发记录.md | 每个提交者 | 同步状态，与代码同提交 |

## 每次工作流程

```bash
git switch main
git pull --ff-only
git switch -c a/viewer-labels
pnpm install --frozen-lockfile
pnpm setup
```

已有未提交工作先保存，不强行切分支。A1/A2 并行工作使用独立克隆或 worktree。B1/B2 串行工作可以轮流使用同一克隆，也可各自克隆；必须先完成上一位交接再接班，不强制创建两套工作目录。B组使用任务分支，如 b/b1-001-numerics、b/b2-003-export，分支名只表达任务归属，不作身份确认或文件隔离。

开发前读日志确认任务未被认领，写入负责人、范围、预计输出；每完成一个能验证的小切片同步日志，不等整项任务结束。

```bash
pnpm check
git add src/team-a/viewer/index.ts 开发记录.md
git diff --cached
git commit -m "feat(a2): [A2-001] improve hardware labels" -m "Role: A2" -m "Task: A2-001" -m "Identity-Source: user-declared"
git push -u origin a/viewer-labels
```

创建 PR 并填写证据。A1/B1 每天集成可运行结果；CI 失败先修复。任何同事或 AI 都必须 fetch/pull 后读取文件；GitHub 不会读取未推送的本地改动。

## 日志条目模板

```markdown
### YYYY-MM-DD / 角色 / 任务ID / 任务标题
- 本次用户身份：A1/A2/B1/B2（填实际角色）；确认来源：本会话用户主动声明/用户回答确认；确认日期：YYYY-MM-DD。
- 负责人：角色；执行者：实际开发者或 AI 标识（如 Codex 代 B1 执行）；分支：xxx；代码基线：SHA；PR：URL或尚未创建。
- 变更：修改目录、问题、实现行为。
- 验证：实际命令、结果、指标、证据；未运行明确标注。
- 当前状态：完成/进行中/阻塞，功能实现不等于验收通过。
- 下一步：具体任务与所属组。
- 跨组影响：接口、依赖、迁移；没有则写无。
- 阻塞/已知问题：如实记录。
```

同时更新顶部状态表。日志追加历史；冲突保留双方条目，不整文件覆盖。通过 git log 定位提交，不把自己提交的 SHA 写入自己形成循环引用。

新增调试/验收日志采用同样的身份字段；机器产生的 JSON/CSV 不便加字段时，配套同目录说明文件记录角色、执行者、任务和对应版本，不修改原始基准。新 Git 提交正文使用独立行 `Role: B1`、`Task: B1-001`、`Identity-Source: user-declared`（按实际角色/任务替换），包括只更新进度的提交。Git author 保留真实执行身份，不把同一机器的 Git 用户当成角色。现有钩子/CI只检查既有边界与开发记录要求，角色声明需开发者和AI遵守、评审核对。

## 检查边界

`pnpm setup` 配置当前克隆的 .githooks。pre-commit 检查 A/B 依赖，以及代码变更是否同时暂存开发记录；CI 对 push/PR 差异重复检查并验证类型、数值和构建。检查不自动生成“已完成”，也不能判断记录真实性。

管理员可给 main 设置 PR 和 verify 必需检查。未启用分支规则前，CI 是检测机制，不能阻止直接推送。不要用 --no-verify 绕过交接规范。

```text
每批代码修改同步开发记录和交接页，调试日志与提交/PR注明角色、执行者和任务ID，代码与记录一起提交到【分支】并推送。
若不能访问 GitHub 或推送失败，明确未同步，不声称其他人已可见。
```
