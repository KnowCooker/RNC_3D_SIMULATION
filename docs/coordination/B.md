# B1/B2 共同任务与串行交接

本页是 B 组共用的任务表和交接入口。B1/B2 不同时工作，继续共用现有源码、测试、日志和本页；只分任务主责，不新增按人员隔离的文件或目录。A/B 两大组之间的源码边界保持不变。

依据：[B组需求](../plan/02_B组独立需求.md)、[每日任务与验收](../plan/03_每日任务与验收.md)、[固定接口](../../src/shared/contracts.ts)。以下拆分针对当前已合入 main 的 demo-v2 范围；A 组未合并草稿中的扩展不自动改变 B 组验收或契约，有跨组新需求时另行确认。

## 1. 开始调试前确认身份

1. 每次新的开发/调试会话先看用户是否已明确声明本次角色。例如“我是 B1”“我本次以 B2 身份继续”。已经明确就直接记录，不重复问。
2. 未声明角色或只说“我是 B 组”时，先问：“请确认你本次是 B1 还是 B2？”收到明确回答后才调试、认领、修改、署名或提交。角色与 B 组范围无关时使用根规则的 A1/A2/B1/B2 选项。
3. `git config --local rnc.role`、GitHub 账号、Git作者、分支名、旧记录都不能代替本次身份确认。用户换人、新会话没有声明或身份有歧义时重新问；同一用户已确认身份的连续工作可以沿用。
4. 确认后可以执行 `git config --local rnc.role B1`（或 B2），只作为最近一次记录。不要将整个仓库默认绑定某个人，不修改 Git作者来假冒用户身份。
5. 认领、调试、验收、更新开发记录/日志以及提交/PR，都注明本次角色、实际执行者和任务 ID。AI 代执行时写“用户角色 B1；执行者 Codex”，而不是仅写“B组”或“AI”。

身份确认是项目中的角色声明，不是账户权限认证；现有钩子/CI不验证用户是否确实属于该角色。

## 6. 串行接班步骤

1. **身份**：采用本会话用户的明确声明；未声明先问。切换B1/B2时在本页及根日志追加接班记录。
2. **保存**：读取 `git status`、分支、开发记录、本页及原仓库开放PR。前任未提交工作保持原样，先确认归属和接续范围；不reset、不整文件覆盖、不强推。
3. **同步**：干净main可 `git pull --ff-only origin main`；已有任务分支先fetch，再按实际需要合入main。前任已推送但未合并的成果从其任务分支/PR核对，不能仅拉main后假定已接到全部工作。
4. **任务**：一次只启动一个B组任务。新功能按根规则先提交认领并建立草稿PR；B1-000是协作文档任务。接续未完成任务时保留任务ID与原主责，补实际接班人、原因和版本；不强迫B2重做B1成果。
5. **验证**：至少跑所属验证、类型与边界，提交前执行 `pnpm check`。数值改变复跑受影响算例；调试日志写明角色、执行者、任务、版本/配置、实际命令、结果与未测内容。证据统一可放 `docs/evidence/B/<任务ID>/`，按任务组织，不按B1/B2隔离。
6. **交接**：代码、根开发记录与本页同批提交；只更新日志也需要署明身份。写精确下一步、遗留项、分支/PR和最新已知SHA，推送后才称远端同步；保存交接后停止写入，由下一位接班。

状态可用：待认领、进行中、待接班、阻塞、待合并、已合并。任务完成、PR合并、设备验收三个状态分别记录。下班时的“待接班”不保证自动唤醒任何AI。

## 7. 统一记录与提交格式

每次开发记录、交接、调试/验收日志至少包含：

```markdown
### YYYY-MM-DD / B1 / B1-001 / 任务标题
- 本次用户身份：B1；来源：本会话用户主动声明（或用户回答确认）；确认日期：YYYY-MM-DD。
- 任务主责：B1；实际执行者：开发者或Codex；接班自：B2/无；分支：...；代码基线：...；PR：URL/未创建。
- 变更与配置：...
- 验证：实际命令、结果、数值容差、证据位置；未执行的明确标注。
- 当前状态：...；未完成/阻塞：...
- 下一步/交接给：具体步骤与B1/B2。
- 跨组影响：无/接口请求及对接人。
```

机器生成的原始结果可保持原格式，配套说明文件写上述元数据并指向对应证据。不得为增加署名修改冻结的数值基准或追改历史Git提交。

新Git提交示例（B2使用实际B2角色和任务）：

```text
test(b1): [B1-001] verify five reference configurations

Role: B1
Task: B1-001
Identity-Source: user-declared
```

角色与任务写在提交说明中，不依赖作者姓名或分支名暗示。PR标题含任务ID，正文写角色、身份确认来源、执行者、范围、验证和交接；合并/squash说明也保留角色与任务，历史作者不变。
